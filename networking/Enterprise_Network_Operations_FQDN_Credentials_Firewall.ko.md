# 엔터프라이즈 네트워크 운영: FQDN 관리, 인증정보 교체 및 방화벽 준비

엔터프라이즈 환경에서 엔드포인트 설정, 인증정보 교체, 방화벽 요청을 관리하기 위한 실무 지침입니다. 아래 패턴은 보편적인 정답이 아니므로 조직의 보안 정책, 서비스 담당자의 요구사항, 네트워크 플랫폼의 기능을 우선 적용합니다.

## 서비스 이름과 엔드포인트 설정 관리

환경별 엔드포인트 설정을 소스 코드 곳곳에 흩어 두지 말고 승인된 설정 관리 시스템에서 관리합니다. 논리적인 서비스 이름과 환경별 설정을 사용하면 엔드포인트 변경을 통제하고 검토할 수 있는 단일 기준으로 관리할 수 있습니다.

CNAME이나 서비스 디스커버리 이름을 사용하면 논리적 서비스 이름과 변경 가능한 백엔드 사이를 분리할 수 있습니다. 단, DNS 소유권, 캐시, 장애 조치 동작, 애플리케이션 구조가 이러한 간접 참조를 지원하는지 확인해야 합니다. CNAME을 추가하는 것만으로 방화벽 정책이 바뀌거나 DNS 변경을 클라이언트와 방화벽이 안전하게 즉시 반영하는 것은 아닙니다. 플랫폼이 지원한다면 인프라 세부정보를 코드에 직접 넣기보다 문서화된 서비스 이름을 사용합니다. 시스템 또는 보안 정책상 직접 IP가 필요할 수도 있습니다.

중앙 설정 시스템은 서비스 URL 등 비밀이 아닌 설정에 사용할 수 있습니다. 인증정보는 승인된 시크릿 관리 시스템에서 별도로 관리하고 애플리케이션에 필요한 최소한의 접근 권한만 부여합니다. `.env`, 애플리케이션 설정, Collection, 스크립트에 인증정보를 커밋하지 않습니다. 환경별 설정을 명확히 분리하고 운영 엔드포인트 변경을 검토합니다.

## 인증정보 교체 계획

서비스 인증정보, 인증서, 소유자, 사용처, 만료 또는 교체 요건을 목록화합니다. 조직 절차에 맞는 주기로 알림을 자동화하고 운영 만료일 전에 교체 절차를 시험합니다.

가능하다면 시크릿 관리자 또는 플랫폼의 네이티브 아이덴티티를 사용합니다. 동적 인증정보, 자동 교체, 런타임 조회는 대상 시스템과 조직의 승인된 아키텍처에 따라 달라집니다. 애플리케이션이 인증정보를 다시 불러오는 방식과 폐기·만료된 값의 처리 방식을 검증합니다.

시스템이 인증정보의 중복 유효 기간을 지원하면 단계적 또는 듀얼 인증정보 교체를 통해 중단을 줄일 수 있습니다. 대체 인증정보를 생성하거나 활성화하고, 소비자를 전환해 정상 동작을 확인한 다음 기존 값을 폐기합니다. 이 방식이 모든 시스템에서 지원되거나 허용되는 것은 아닙니다. 제공자 제한, 아이덴티티 정책, 감사 요건, 담당 팀의 실행 절차를 따릅니다. 명시적인 승인 없이 공유 계정이나 추가 장기 인증정보를 만들지 않습니다.

## 최소 권한 방화벽 요청 준비

서비스 구축 초기에 통신 매트릭스를 작성하고 서비스가 동작하는 데 필요한 흐름만 요청합니다. 요청 주체, 목적지 서비스, 환경, 통신 방향, 프로토콜, 목적지 포트, 업무 목적, 담당자, 요청 기간을 명시합니다. 정확한 호스트 또는 승인된 최소 범위를 지정하며, 서브넷 전체를 기본값으로 요청하지 않습니다. 동적 워크로드 등으로 더 넓은 출발지 범위가 정당화된다면 아키텍처와 위험을 별도로 검토합니다.

| 환경 | 출발지 워크로드 / 승인 범위 | 목적지 서비스 / 승인 이름 | 프로토콜 / 포트 | 목적 | 담당자 / 만료 |
|---|---|---|---|---|---|
| 테스트 | `<승인된 출발지>` | `auth.example.com` | TCP / 443 | 테스트 인증 요청 | `<담당자>` / `<날짜>` |
| 테스트 | `<승인된 출발지>` | `api.example.com` | TCP / 443 | 테스트 API 호출 | `<담당자>` / `<날짜>` |
| 운영 | `<승인된 출발지>` | `<승인된 목적지>` | `<프로토콜> / <포트>` | `<업무 목적>` | `<담당자>` / `<날짜>` |

예시와 공개 문서에는 자리표시자만 사용합니다. 실제 요청에는 네트워크 및 서비스 담당자가 승인한 값을 기입합니다. 편의를 위해 출발지, 목적지, 포트 범위를 넓게 요청하지 않습니다. 적절한 경우 프록시나 API Gateway를 통해 아웃바운드 통신을 중앙화할 수 있지만, 용량, 소유권, 인증, 장애 동작을 설계에 포함해야 합니다.

FQDN 기반 방화벽 규칙은 IP 기반 규칙을 보편적으로 대체하는 방법이 아닙니다. 방화벽이 필요한 FQDN 규칙 유형을 지원하는지, DNS 레코드의 조회 및 갱신 방식, TTL, 여러 A/AAAA 응답, CNAME 체인, DNS 장애 처리 방식을 확인합니다. 규칙은 각 연결에서 호스트명을 검사하는 대신 DNS 조회 결과의 IP를 사용할 수 있으며, DNS 변경이 정책에 즉시 반영되지 않을 수 있습니다. 네트워크 팀 및 애플리케이션 담당자와 설계를 검증합니다.

## 승인된 네트워크 변경 검증

변경 작업 후 승인된 출발지 호스트와 환경에서 허가된 목적지 및 포트만 테스트합니다. DNS 조회, TCP 연결, 애플리케이션 응답을 각각 확인합니다. TCP 연결 성공이 TLS, 인증, 애플리케이션 정책까지 정상임을 의미하지는 않습니다. 역방향으로 별도 연결을 시작해야 하는 설계일 때만 역방향 흐름을 테스트합니다. 상태를 추적하는 방화벽은 일반적으로 이미 맺은 연결의 응답 트래픽을 허용합니다.

```sh
# 승인된 서비스 이름의 DNS 조회를 확인합니다.
nslookup api.example.com

# 승인된 출발지에서 허가된 호스트와 포트만 테스트합니다.
nc -zv -w 3 api.example.com 443

# 승인된 헬스 엔드포인트를 확인합니다. HEAD를 지원하지 않으면 GET을 사용합니다.
curl --silent --show-error --output /dev/null \
  --write-out 'HTTP %{http_code}\n' --connect-timeout 3 \
  https://api.example.com/health
```

테스트 승인 및 진단에는 내부 절차를 따릅니다. 관련 없는 호스트나 포트를 스캔하지 않습니다. 연결에 실패하면 시각, 출발지 식별자, 조회된 목적지, 포트, 민감정보를 제거한 오류를 기록하고 담당 팀과 DNS, 라우팅, 방화벽 결정 로그, 프록시 설정, 서비스 상태를 확인합니다. 증거 자료에서 인증정보와 민감한 응답 데이터를 제거합니다.

## 운영 체크리스트

- 논리적 서비스 이름과 환경별 설정, 담당자를 연결한 엔드포인트 목록을 관리합니다.
- 방화벽 요청 번호, 승인된 흐름, 출발지·목적지 범위, 포트, 승인 상태, 검토·만료일, 갱신 담당자를 추적합니다.
- 인증정보와 인증서 담당자, 시크릿 관리자 참조 경로(시크릿 값은 제외), 교체 요건, 검증 상태를 관리합니다.
- 안전한 자리표시자를 사용한 Postman Collection을 공유하고, 민감한 값은 명확한 접근 정책을 갖춘 승인된 Vault에 둡니다.
- 워크로드, 서비스 담당자, 환경, 네트워크 설계가 바뀌면 접근 권한을 재검토하고 더 이상 필요하지 않은 규칙과 인증정보를 제거합니다.
